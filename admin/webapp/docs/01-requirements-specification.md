# NeuVector Web 前端需求规格说明书

## 1. 文档说明

| 项目     | 内容                                                      |
| -------- | --------------------------------------------------------- |
| 文档对象 | `admin/webapp` NeuVector Security Center Web 前端         |
| 文档性质 | 基于现有实现反向整理的现状规格（As-Is Specification）     |
| 适用版本 | `package.json` 标识版本 5.0.0，代码基线为本文生成时工作区 |
| 读者     | 产品、研发、测试、运维、安全评审人员                      |
| 需求等级 | “应”表示现有代码可确认的系统能力；“宜”仅用于质量约束      |

本文以路由、页面组件、公共业务组件、服务、类型定义、接口常量及中英文资源为依据。
它描述前端已经实现并暴露的能力，不替代后端 REST API、部署规格或产品商业授权说明。

## 2. 产品目标与范围

NeuVector Web 前端是容器安全管理平台的浏览器端控制台，应为用户提供以下闭环能力：

1. 统一查看集群、工作负载及安全风险态势。
2. 盘点平台、命名空间、节点、容器、镜像仓库和系统组件。
3. 配置准入、分组、网络、响应、DLP、WAF 等安全策略。
4. 分析漏洞、合规项、安全事件、系统事件和风险报告。
5. 管理本地及联邦集群、联邦策略和成员集群切换。
6. 管理用户、角色、API Key、认证服务器、系统配置及支持数据。

### 2.1 系统边界

前端负责页面呈现、交互校验、权限展示控制、请求编排、结果格式化、报表生成和本地会话状态；
资产发现、策略执行、扫描、事件采集、认证判定和数据持久化由 NeuVector Manager 后端负责。

### 2.2 运行环境

- 应以单页应用方式运行，使用 Hash 路由，默认入口为 `#/login`。
- 应通过同源相对地址访问 Manager REST API。
- 应支持英文和简体中文资源，并允许合并伙伴定制翻译。
- 应支持开发构建、生产构建以及 Karma/Jasmine 单元测试。

## 3. 用户与权限

| 角色/身份           | 需求描述                                                  |
| ------------------- | --------------------------------------------------------- |
| 未认证用户          | 可进入登录、EULA 和单点登录跳转流程；不可访问受保护数据。 |
| 全局管理员          | 可在授权范围内管理资产、策略、用户、认证、配置及集群。    |
| 联邦管理员          | 可管理联邦配置、联邦策略及成员集群，并切换管理上下文。    |
| 只读用户            | 可查看被授权资源，修改类操作应隐藏或禁用。                |
| CI/Ops 或自定义角色 | 功能由后端下发的全局、远程全局、域和附加权限共同决定。    |
| 命名空间用户        | 仅查看获授权域数据，系统级配置等能力应受限。              |

权限判定应同时考虑资源所需级别、用户角色权限、集群角色（独立/主集群/成员集群）和当前是否为远程集群。
前端权限控制是交互约束，后端仍必须对每个 API 执行最终授权。

## 6. 外部接口需求

### 6.1 REST 接口域

前端应通过相对路径调用以下接口域；完整参数和返回结构以后端 API 契约为准。

| 接口域       | 代表性资源                                                                               |
| ------------ | ---------------------------------------------------------------------------------------- |
| 认证与授权   | `auth`、`self`、`user`、`role2`、`api_key`、`server`、`password-profile`                 |
| 资产与扫描   | `host`、`workload`、`container`、`domain`、`controller`、`scanner`、`enforcer`、`scan/*` |
| 网络         | `network/graph`、`network/session`、`network/history`、`network/conversation`、`sniffer` |
| 策略         | `group`、`service`、`policy`、`admission/*`、`responsePolicy`、`dlp/*`、`waf/*`          |
| 风险         | `risk/cve`、`vulasset`、`risk/compliance`、`risk/*/profile`                              |
| 事件与仪表盘 | `event`、`audit`、`security-events2`、`dashboard/*`、`summary`                           |
| 联邦         | `fed/*`、`multi-cluster-summary`、带 `scope=fed` 的策略接口                              |
| 配置与支持   | `config-v2`、`file/config`、`file/debug`、`usage`、`csp-support`、`remote_repository`    |

### 6.2 文件接口

- 应支持 YAML/配置文件导入导出、CSV 下载、浏览器打印/PDF 和 PCAP 下载。
- 文件导入应携带当前认证信息并反馈成功、部分失败或错误详情。
- 导出文件应使用明确的业务文件名，远程仓库导出应支持预定义文件名。

## 7. 非功能需求

### 7.1 安全性

- 令牌不得写入日志或 URL；现有拦截器通过 `token` 请求头传递令牌，后端必须仅在受保护传输通道中接收和校验。
- 敏感表单字段应使用密码型控件；前端不得硬编码凭据。
- 所有输出仍应依赖 Angular 模板转义，外部链接和下载地址须经过可信处理。
- 导出的 CSV 内容应防范公式注入；后端错误不宜泄露秘密信息。
- 权限隐藏不可替代后端鉴权。

### 7.2 性能与容量

- 主业务路由应延迟加载，避免一次加载全部功能模块。
- 大型漏洞、事件和镜像数据应采用服务端分页、分批查询或无限滚动。
- 网络拓扑应按设备能力选择渲染方式并支持过滤，避免不可控节点量。
- 生产首包构建预算：警告 14 MB、错误 16 MB；单组件样式警告 15 KB、错误 30 KB。
- 资产报告单次处理约束以实现常量为准：总计最多 100000 条、每页最多 10000 条。

### 7.3 可用性与兼容性

- 界面应适配桌面端常见宽度，主要设置和集群页面应响应窗口尺寸变化。
- 应提供中英文文本、日期/时间和状态的统一格式化。
- 应满足键盘操作、可读标签、对比度等基本可访问性要求；具体合规等级需另行验收。
- 构建目标为 ES2019；实际浏览器支持矩阵由部署版本的浏览器策略决定。

### 7.4 可靠性与可维护性

- HTTP 失败应保持页面可恢复，允许用户重试；超时应进入统一登录恢复流程。
- 组件销毁时应停止定时器、图形实例和订阅，避免重复刷新和内存泄漏。
- TypeScript、模板和依赖注入应启用严格检查。
- 业务组件应配套 `*.spec.ts` 单元测试，关键行为变更应增加回归覆盖。
